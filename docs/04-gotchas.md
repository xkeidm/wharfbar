# 04 — Traps and Mitigations

| Trap | Mitigation |
|-------|---------|
| A crash before the AppBar registration is removed → a stuck work area | `ABM_REMOVE` on `OnClosing` + `Exit` + the unhandled path if possible; during development, restart `explorer.exe` |
| A shell/explorer restart → the AppBar registration is lost | A re-registration strategy (a shell message / a health check) |
| Overriding a WPF-UI brush key on the bar window (`Resources["TextFillColorPrimaryBrush"] = …`) leaks into flyout popups | Popup children resolve resources through the logical tree up to the bar window, so a window-level override re-colors opaque flyout surfaces with wallpaper-tinted text. Bar-scoped overrides use **unique keys** (`Bar.TextPrimary`, `Bar.HitFill`, `Bar.PillFill`, … in `TopBarContrastPalette`): only the bar's own styles reference them; popups keep resolving the WPF-UI keys from the app dictionaries |
| A transparent top bar over a light wallpaper in dark mode | The theme-driven brush is invisible; the wallpaper-driven palette measures the strip behind the bar (`WallpaperTopStrip`, cached per path) and flips the text tone automatically — see `.agent/screens/topbar.md` |
| `AllowsTransparency=true` + Mica | Never use them together; a WPF-UI backdrop, or opaque + DWM extend. Dock Mica mode is not layered (window = plate). A tint/transparent dock is layered and does not carry DWM Mica. Flyout popups use `AllowsTransparency=true` because they are a separate window (`PopupAnimation=Fade` requires it); they do not affect Mica |
| DWM Mica on a full-screen layered overlay | WPF-UI theme applies (startup / theme) can also bind `DWMWA_SYSTEMBACKDROP_TYPE` **to the overlay window**; in the dark theme an opaque `#202020` covers the whole screen, and the desktop/windows are invisible (the overlay comes out as a solid color, not translucent). `VeilWindow` clears it with `Dwm.SetSystemBackdrop(None)` on every show + on `WM_THEMECHANGED`/`WM_DISPLAYCHANGE`/`WM_DPICHANGED`; after startup, `ReassertBackdrop` makes sure again. **Startup order is critical:** while the overlay is off, the window is never created (`VeilService` calls `EnsureWindow` only when enabled); even when it is on, `App.OnStartup` applies the theme **first**, and the overlay window is realized **after** that — otherwise the theme apply binds Mica to a fullscreen window that was just created, and the ~1-second opaque "overlay" flash at startup is visible |
| Quick settings / PolicyConfig | `IPolicyConfig` for the default audio device (ADR-006); not tray RPM |
| Volume mixer | Change the default with a single selected output device + an inline expander (do not use a nested `Popup` inside the QS `Popup` — focus escapes and the list is invisible); master `IAudioEndpointVolume` + the session list; `IMMDeviceCollection` IID `…8397-CC5392387B5E`; wrap the `IAudioSessionEnumerator` ComImport with the IUnknown IID (an official-IID QI gives `E_NOINTERFACE`, and the vtable is still the enumerator); do not rebuild the rows while a session slider is being dragged (a poll/`Changed` mid-drag was tearing down the UI); an MDL2 session icon if there is no process path; UWP icons are limited (ADR-006) |
| WPF-UI backdrop + raw DWM at the same time | WPF-UI first; keep raw DWM as the fallback |
| `WindowChrome` / caption + a 30 DIP strip | Caption min-height ~39 px; `WindowStyle=None` + frame extend (ADR-004) |
| `SystemThemeWatcher` overwrites the wanted backdrop | The watcher pushes the default Mica; handle theme messages with `WindowAppearance.Refresh` |
| Redefining a `ContextMenu`/`MenuItem` style without `BasedOn` | The WPF-UI Fluent templates drop out; an Aero2 light-gray icon column + a dark menu body → `SymbolIcon` disappears. In `App.xaml`, BasedOn `UiContextMenu` / `UiMenuItem` / `WpfUiMenuItem`; set only the font |
| A rounded DWM corner on an edge strip | DWM rounds all four corners at once; the top bar uses `DONOTROUND` |
| A DPI change / a monitor plug-unplug | Per-Monitor V2 + `WM_DPICHANGED` + display handlers; SETPOS the AppBar again on every monitor; at mixed DPI each window is computed with its own monitor's DPI (per-window) |
| A multi-monitor AppBar | Each monitor has its own AppBar (the bar is moved to the target monitor and `ABM_NEW`); if shell compatibility is fragile on secondary monitors, the `SPI_SETWORKAREA` fallback |
| Trying to read system / foreign tray icons | ADR-009: a read-only mirror + `SendMessage` click-forward only via documented comctl32 `TB_*` messages; no `ToolbarWindow32`/RPM/injection. `SendMessageTimeout` (`SMTO_ABORTIFHUNG`, 500 ms) prevents a UI lock on a hung explorer. Hidden/overflow icons cannot be mirrored (they exist only in the open popup) → `Win+B`. |
| The tray mirror is empty on Windows 11 25H2 | The classic `ToolbarWindow32` tray was removed on 25H2 (there is no `SysPager`/`ToolbarWindow32` under `TrayNotifyWnd`; the icons are in XAML composition). `FindToolbarHwnd` is empty → `TrayMirrorService` falls back to UIA. UIA children are visible only while the taskbar is `SW_SHOW` → the read requires `BeginTrayPeek(stealth:true)` (cloak + off-screen); while fully `SW_HIDE` it returns empty. A parked auto-hide bar keeps its buttons virtualized even when shown in place, so the quiet read recreates the click gesture — a bottom-edge hover reveal (`TrayAutoHideReveal.TryReveal`, cursor restored, no work-area change) gated by `TrayRevealPolicy` (pointer idle ≥1.5 s or the mirror still empty, no fullscreen app) — before it captures. Icon: `TrayCapture.PrintWindow(PW_RENDERFULLCONTENT)` draws the parked+cloaked taskbar + the button's `Image` child rect is cropped (the real icon, no flash; a letter glyph if the capture fails). A right/double click cannot be expressed with UIA → a visible peek + a physical click (a short flash, accepted). |
| Tray mirror reorder crashes (`ArgumentOutOfRangeException` on `Items.Insert`) | `ApplyTrayMirror` used `RemoveAt(current)` + `Insert(i, host)` against `visible.Count`. UIA keys by name/tooltip, so duplicate keys leave `Items.Count < i`, and Insert throws (unhandled → process exit). Unnamed and repeated buttons now get index-suffixed keys (`TrayMirrorOrder.UniqueKeys`, `name\0#index`), so no button is lost to de-duplication; reorder with `TrayMirrorOrder.SyncOrder` (clamped insert). |
| A taskbar flash during a stealth peek | UIA children are exposed only while `Shell_TrayWnd` is `SW_SHOW` (verified by probe: while `SW_HIDE`, `NormalButton count=0`; **also 0 in the auto-hide slid-out state** — the auto-hide path is dead). On some machines DWM cloak is rejected; a park+show without cloak flashes when explorer writes the position back. Also, when the primary bar is shown, explorer sync-shows the secondary bars **asynchronously** — the reaction can land AFTER the peek cleanup, and per-peek style restore makes those late shows visible. The model: a **permanent stealth style** — `WS_EX_LAYERED \| WS_EX_TRANSPARENT + alpha 0` stays on every tray hwnd for the life of WharfBar (`EnsureTrayStealthStyles`, idempotent; it also catches new secondaries); visibility is restored only for a visible peek (`SetTrayVisible(true)` → `ClearStealthVisuals`) and on exit. NO move/resize (`SetWindowPos` alone triggers a sync). |
| A tray read makes the desktop and the windows jump | `ABM_SETSTATE(0)` ↔ `ABS_AUTOHIDE` opens and closes the work area; in the diag, `stealth-show-alpha` once a minute, `cloak=False`. Refresh first tries the quiet read — a stateless stealth peek plus hover reveal (`refresh reveal`). If an icon arrives, the session does not do a state blip. **Decision changed 2026-10-14 (live report: windowed apps kept jumping; diag: `refresh state-blip` ~6–9 s after each click, and every click itself showed the tray at `y=1032` = strip reserved):** the 3 min state-blip cadence plus the click follow-up/theme/retry expedites landing on the state path, plus `BeginIconRefresh` on every click, flapped the work area several times a minute. Now: (1) expedite requests only drive the quiet reveal; (2) the state blip goes through `TrayStateBlipGate` — once per explorer instance (bootstrap, skipped while maximized), then only after ≥10 min (mirror still empty) / ≥20 min (upkeep, and only in a shell that already blipped) with the user idle ≥3 min and no maximized/snapped/bottom-touching window (`TrayAutoHideReveal.HasWindowAffectedByWorkAreaChange`); (3) a click reveals the auto-hide tray by hovering the bottom edge (no work-area change) and drops the state only if that reveal fails; (4) an empty read is only evidence when a **revealed** tray actually read back zero buttons (`TrayBlipOutcome.ConfirmedEmpty`, confirmed by a second read 220 ms later); every "never looked" outcome (throttled, busy, fullscreen, reveal timeout, UIA walk threw) holds the last good snapshot — **a stale icon is preferred over a jump**. Every tray-driven flip is counted in the diag log: grep `state-change #` (reasons `refresh-Bootstrap`, `refresh-Maintenance`, `click-fallback`, `overflow`). Why show-only stays empty here: in the strip-release `ABS_AUTOHIDE` state explorer parks the tray at `y=1078` and virtualizes its XAML content; a stealth show does not unpark it, so UIA reports 0 buttons. In the blip window `LockWindowUpdate(desktop)` stops the paint from drawing the intermediate size. If the gap has not changed at the end of the stealth peek, `WorkAreaChanged` is not fired. |
| On multiple screens a background setting does not hold on one bar | Decompiled WPF-UI 4.3.0 facts: `ResourceDictionaryManager.UpdateDictionary` does not compare URIs — **every** `ApplicationThemeManager.Apply` call refreshes the dictionary and runs `WindowBackgroundManager.UpdateBackground(Application.MainWindow, …)`; `RemoveBackdrop` → `RestoreContentBackground` paints the MainWindow opaque (`CompositionTarget.BackgroundColor = SystemColors.WindowColor`). **While backdrop=None, this opaque paint is not cleared.** So any window's Tint/Transparent apply leaves the primary bar (MainWindow) opaque. In the old code `ApplyTranslucent` never fired the clobber event → the primary stayed wrong and the secondary stayed right. The fix is a trio: (1) `EnsureApplicationTheme` — if `GetAppTheme` is the same, skip the global Apply entirely (no clobber on mode/opacity changes); (2) `ApplyTranslucent` also fires the clobber event, and only the current MainWindow handles it (everyone handling it produces a secondary↔secondary infinite recursion); (3) after the settings pages' direct library applies (theme/accent; the default backdrop pushes Mica!) all bars are re-confirmed with `ApplyTopBarChanges`. |
| A tray-icon click goes to the wrong application | If the button order shifts between snapshot polls (an icon added/removed), the index can stay stale; the next 4 s poll fixes it. Double click: on the first click WPF also raises `MouseLeftButtonDown` → the forwarded sequence is `down/up, down/up, dblclk/up` (native is `down,up,dblclk,up`); applications ignore the extra down/up. |
| Clicking a mirrored icon does nothing / the menu opens at the bottom edge | Application flyouts/menus are anchored to the real `Shell_TrayWnd`; while the bar is invisible, InvokePattern looks as if nothing happened. Moving the bar under the top bar with `TryMoveTrayNear` was tried — it had **0 successes in a 49k-line diag log** because explorer takes the AppBar position back immediately; it was removed. The current flow: a stealth peek (`BeginTrayPeek(stealth:true)`) → `BeginTrayClickInput` (alpha 0→1, click-through is removed) → **hover reveal** (`TrayAutoHideReveal.TryReveal`: the cursor goes to the bottom edge under the icon and explorer slides the auto-hide tray on screen without reserving a work area; the cursor is restored after the session; after 2 misses in a row the reveal is skipped for 10 min and the click drops the state instead, logged as `state-change … click-fallback`) → the button rect is read again from the live tree (falls back to the rect recorded on the last unparked read) → a `SendInputMouse` physical click → **the flyout/menu opens at the bottom edge of the screen** → `TrayMenuReanchor.TryReanchor` moves the newly appeared popup window around the clicked button (the click region) (a Win32 `#32768` menu, or the app flyout in the region) **under the mirror icon** (`SetWindowPos`, work-area clamped; a 2.5 s watcher — the click path used to pass a 1 s budget and Phone Link's late popup hit `reanchor timeout (no candidate)`; fullscreen overlays excluded). The pre-click snapshot skips **cloaked** windows (XAML/UWP flyouts are pre-created visible-but-cloaked and uncloak on the click, so snapshotting them hid the target). After the move a bounded re-assert (1.5 s, ≤4 moves, 8 px tolerance, `reanchor reassert` in the log) puts back popups whose owner re-positions them after its show animation (EarTrumpet-style). Matching is NOT by pid — every 25H2 XAML button reports the explorer pid (verified with UIA), so pid cannot tell them apart. If there is no anchor (a shell-hosted flyout outside the region, and similar), the menu stays where it opened — a remaining limitation. Three behaviors had been observed per application (ones that read the cursor open at the top, ones anchored to the rect throw to the bottom edge, AMD sticks to y=0); re-anchor brings all of them to a single point. The peek stays open until the menu has been repositioned (at most 1 s) and the cursor stays on the real button during that time — a cursor taken back at a fixed 160 ms was dropping the menu for slow owners (Command Palette, a cold first click); in the diag the first right click is `reanchor timeout`, and the menu appears on the next click. A popup that belongs to the tray (`GW_OWNER` = `Shell_TrayWnd`) is detached with `GWLP_HWNDPARENT`, otherwise `SW_HIDE` at the end of the peek also closes the menu. The busy-join is in the background. The click chain does not wait for a fixed settle: a resolve-first loop (10×100 ms) clicks as soon as the live tree is ready. Empty-named mirror items do NOT match by containment (every string contains the empty substring → it would click the wrong application); it is resolved with the poll-time index (`TrayButtonMatcher`). **A right click is not forwarded on `MouseDown`** — while the button is down the top bar has mouse capture, so the injected right click goes to WharfBar rather than the tray button and the owner's menu does not open; forwarding is on `PreviewMouseRightButtonUp` (`Handled` in the tunnel so `StatusStrip` does not open its own menu). Immediately before the physical click, `AllowSetForegroundWindow(ASFW_ANY)` (otherwise `TrackPopupMenu` cannot take focus). The `SendInput` coordinate is inside the packet (`MOUSEEVENTF_ABSOLUTE`); the cursor stays on the real button until the menu appears (at least 160 ms, at most 1 s) because the owner reads `GetCursorPos`. The re-anchor snapshot is taken **before** the click. WharfBar does not draw the menu — the content is the owner's HMENU / flyout. |
| Mirror icons disappear for 1–2 s and come back | Every peek tears down and rebuilds the Shell's XAML content; a tree read without waiting after SW_SHOW returns empty/partial. The fix: a 160 ms settle before the read, and an empty direct read never clears the snapshot any more — only a **revealed** tray that reads back zero buttons (after a 220 ms confirmation read, `TrayBlipOutcome.ConfirmedEmpty`) does. A rebuilding tray therefore no longer blanks the bar. |
| The tray mirror refresh moves the mouse | The quiet read cannot see the parked auto-hide tray's virtualized buttons, so it hovers the bottom edge (real input, like a click) and waits for explorer to slide the tray in; the cursor is restored afterwards (only if it is still parked on the reveal point — a user-moved pointer is never yanked) and no work area changes. That hop is visible, so it only runs while the pointer is idle (`TrayRevealPolicy.ShouldAttemptReveal`, ≥1.5 s since the last input) or while the mirror is still empty (a short hop beats a blank bar; capped at 3 such attempts per shell), and never while a real fullscreen app covers the primary monitor. After 2 consecutive reveal misses the quiet read is skipped for 10 min (`TrayRevealPolicy.IsRevealBackedOff`), shared with the click path. WharfBar's own auto-hide dock keeps its edge-band show suppressed while a stealth peek owns the cursor (`DockAutoHideController.ShouldShowForCursor`), otherwise every refresh would pop the dock. Never widen this gate to "any refresh": a busy user would have the cursor yanked mid-work. |
| A WPF-UI `SymbolRegular` is missing from XAML | E.g. `Meter24` is missing → the Settings `GeneralPage` parse blows up and the process dies. Verify the enum name in the package (`DataUsage24` and similar) |
| Only the clock is visible on the top bar | A WPF-UI `SymbolIcon` can come out empty on a Mica AppBar; use a Segoe MDL2 `TextBlock` for status/overflow |
| The left brand logo is not visible | Do not use MDL2 for it; draw `BrandLogo.BarGlyph` geometry (independent of the font). Exe/tray/About use `Assets/WharfBar.ico` / `.png` |
| □□□□ (tofu) in status tooltips | An MDL2 glyph inherits the string `ToolTip` font on a `TextBlock`; make the `ToolTip` style Segoe UI / use `SetPlainToolTip` |
| Clicking “Hidden icons” does nothing | Win+B does nothing while the taskbar is parked with `ABS_AUTOHIDE`. Overflow uses `BeginIconRefresh` (`SetState(0)`) + `BeginTrayPeek` (a mirror click now reveals by hover first and uses the state drop only as a fallback); on close, `EndIconRefresh` puts the strip back. This flip still moves windows and is counted as `state-change … overflow`. If the peek does not open, the state does not leak. |
| A repeated dock click does not minimize | `LaunchOrActivate` was only activating; if it is in front, `SW_MINIMIZE`. `CaptureForegroundHint` (`GetForegroundWindow`) before the dock steals focus |
| Dock icons are blurry / far too large | The `dock.iconSize` default is 24 DIP. Glyph: `SHGetFileInfo(SHGFI_ICONLOCATION)` + `SHDefExtractIcon` (the desired px), otherwise `SHGFI_SYSICONINDEX` + `IImageList` jumbo (256) / extra-large (48). Do not scale a 16/32 `SHGFI_LARGEICON` bitmap up into a large slot. Drawing uses `UseLayoutRounding` + `SnapsToDevicePixels` |
| The dock sits above the screen edge | While the taskbar is hidden a work-area gap can remain; for the dock's Y, use the monitor's bottom edge |
| A tray icon is drawn as a black square | `PrintWindow(PW_RENDERFULLCONTENT)` **returns `TRUE` without writing any pixels into the DIB** while the taskbar `IsWindowVisible=False`; because `TryCaptureWindow` did not check that, an empty bitmap is published as a successful icon and the letter glyph never kicks in. The measured difference: peek closed → `visible=False`, pixels `[0,0,0,255]`; peek open → `visible=True`, pixels `[67,67,67]…`. **alpha 0 is not the obstacle** — the only determinant is the peek being open. The fix: `TryRefreshViaBlip` captures the icons **before** `EndTrayPeek`; `TrayCapture.IsBlankCapture` also rejects a single-color/fully transparent crop (letter-glyph fallback). If the capture is moved outside the peek, it **always** goes back to a black square |
| A mirrored tray icon keeps its old state (Discord mute/call icon stays lit or dim) | **Root cause (2026-10-14, diag log + code):** pixels can only be captured inside a peek, and the refresh peek ran **only when the direct UIA read was empty**. Where the direct read returns buttons, `CachedIcon(refresh:false)` reused the name-keyed bitmap for the whole session (the tooltip `Discord` never changes); where it is empty, the show-only probe latched `false` after a single empty read at startup (parked auto-hide tray at `y=1078`) and the state blip ran once every 3 min — the log showed exactly that cadence. **Fix:** the refresh runs on its own cadence regardless of the direct read (`TrayIconRefreshPolicy`): show-only 60 s, 20 s while a refresh found changed pixels, state blip still 3 min; an expedited refresh (floor 15 s) after a mirror click (+6 s), after a theme/accent change (+3 s) and once after an inconclusive peek. One `PrintWindow` per peek (`TrayCapture.TryCaptureFrame`) and per-button crops; `TrayIconSignature` (FNV-1a over the crop) + `TrayIconCache` return the **cached instance** for unchanged pixels and the publish is skipped when the snapshot is the same (`TrayMirrorDiff.IsSameSnapshot`), so a steady 4 s poll touches no UI. A failed crop keeps the last real icon (no glyph flicker) up to 10 min, then the glyph. **Limit (revised the same day, see the jump row):** on a machine where only the state blip exposes the parked tray, background refresh is off; icons refresh when a mirror click reveals the tray (re-capture if the last one is ≥15 s old) or on the rare idle-gated upkeep blip. An icon change not triggered through the mirror can stay stale — accepted over a jumping desktop |
| Mirrored tray icons sit on a taskbar-coloured square | `PrintWindow` renders the tray with its own opaque fill, so a raw crop carries the dark/light taskbar background onto the top bar. `TrayCapture.TryCropIcon` crops a 3 px ring around the button's icon rect, takes the per-channel median as the background, and `TrayIconMatte.RemoveBackground` unblends every pixel colour-to-alpha (channel distance ≤12 = transparent, then a soft ramp; straight-alpha `Bgra32`), so anti-aliased edges stay soft in both themes. The signature is computed over the matted pixels. A theme change re-captures (new background → new signature). `TB_GETIMAGELIST` does not exist on the 25H2 XAML tray, so the colour key is the only documented route there |
| A gap under a maximized window (dock hidden) | **RESOLVED (ADR-005 note 5; verified again on 2026-09-30):** the hide flow issues `ABM_SETSTATE(ABS_AUTOHIDE)` and stays in that state while running — explorer parks the bar in an ~2px clamp and removes the bottom reservation from the work area, and maximized windows cover the full screen. Measured while WharfBar **is running**: `ABM_GETSTATE=1`, `Shell_TrayWnd` invisible, `SPI_GETWORKAREA.Bottom`=1080 (the bottom of the monitor) → **bottom gap 0**; while the application is closed, 1032/48. (Background: `SPI_SETWORKAREA` is dead on 25H2 — it returns `TRUE` and is silently ineffective, so the circuit breaker has to **verify the effect**. A per-window `SetWindowPos` compensation was removed because it produced a 7 ms fight with Firefox/WinForms.) **Trap:** only **a registered AppBar** drives this state; probing it from the outside returns `TRUE` and does nothing, which produces the wrong conclusion that "the API is dead" |
| A maximized window growing and shrinking (oscillation) | Every expansion done with `SPIF_SENDCHANGE` makes explorer re-approve the hidden taskbar's reservation (~48px) → the work area jumps 1032↔1080 once a second, and maximized windows keep changing size. The solution: broadcast only the **startup** announcement (`ApplyHide(broadcast:true)`); every maintenance expansion is **silent** (f=0). A silent write does not trigger an explorer recalc (0 ghosts in 12 s). `SetDockReservation` broadcasts once on changes; the following ghost is repaired silently. **25H2+:** the expansion cannot be applied at all anyway (the trap above) — the oscillation is not seen either; the circuit breaker swallows the dead call |
| While the dock is visible, a maximized application overlaps the dock / goes under it | While `dock.autoHide=false`, `DockWorkAreaReservation` reserves a full-width `ABE_BOTTOM` at the plate height (the plate itself is not an AppBar). The maximized window stops at this line. Auto-hide calls `ABM_REMOVE`. `SPI_SETWORKAREA` is dead on 25H2. The strip is **not painted**: a WPF `HwndSource` ignores `LWA_ALPHA` because of DWM redirection and stamps the strip black; the window is raw `CreateWindowEx` + alpha 0, the wallpaper is visible, and the click passes through. Desktop icons use the same work area, so they stop at the same line — Windows does not separate that from a maximized window |
| UWP icons | No full support in v1; a placeholder, or skip; do not offer a broken Appx path |
| The restore is missed after hiding the taskbar | At startup, capture `ABM_GETSTATE` + `SPI_GETWORKAREA`; on exit, **always** `ShowWindow(SW_SHOW)` + `ABM_SETSTATE(baseline)` + the baseline `SPI_SETWORKAREA`, then `ABM_REMOVE`; `IsWindowVisible` misleads during auto-hide — do not use it on restore. **25H2+:** the baseline `SPI_SETWORKAREA` restore is skipped by the circuit breaker — harmless: once the tray comes back with `SW_SHOW`, explorer re-approves the strip itself. `ABM_GETSTATE` is also unreliable on 25H2 (measurement: it reads 0 even when `ABS_AUTOHIDE` was written). Closing the top-bar window is **not an exit path** — `TopBarWindow.OnClosing` only releases the shell state (`ReleaseShellState`); because `ShutdownMode` leaves other windows open, the process keeps living; exit = the tray menu → Quit |
| Choosing the taskbar hide API | `ShowWindow` + `SWP_HIDEWINDOW` (`Shell_TrayWnd` + `Shell_SecondaryTrayWnd`). `ABS_AUTOHIDE` brings the bar back with edge reveal — it is not used while hiding. Restore is `SW_SHOW` + the `ABM_SETSTATE` baseline. **25H2+:** `SPI_SETWORKAREA` (bottom edge = the monitor) is dead — an ~48px ghost strip remains after `SW_HIDE`; the work area cannot be expanded (see "A gap under a maximized window") |
| The taskbar becomes visible again after it was hidden | Explorer shows `Shell_TrayWnd` again with an AppBar `SETPOS` / `Shell_NotifyIcon`; `ABS_AUTOHIDE` triggers edge reveal (it is not used while hiding). Keep-hidden is a 250 ms `FindWindow`/`FindWindowEx` + `SW_HIDE` if needed (there is no full `EnumWindows` on the UI). Keep-hidden **runs on a background `System.Threading.Timer`** (dispatcher starvation cannot stop the re-hide); the peek protects the tray only while it is fresh — a stuck peek is force-ended after 45 s, so the taskbar can never stay visible forever. Even while the HWND is hidden, the taskbar AppBar reservation can come back; keep-hidden tries a **silent** work-area expansion once a second (no `SPIF_SENDCHANGE` — a broadcast pushes explorer back to SETPOS and produces the oscillation loop, the trap above). **25H2+:** the expansion call is skipped by the `WorkAreaExpandPolicy` circuit breaker (a single probe once every 10 min, instead of hitting a dead API once a second). `SPI_SETWORKAREA` (`SPIF_SENDCHANGE`) broadcasts to every top-level window and blocks for ~1 s on this machine — the call was moved to a background thread so the UI thread (the top-bar menu / settings) does not freeze; an expansion that races with restore is rolled back to the baseline. There is no `ReapplyHide` inside `ApplyPlacement`. `ABN_POSCHANGED` does not call `SHAppBarMessage` inside explorer's `SendMessage` (`BeginInvoke`); `ABM_SETPOS` only when the QUERYPOS rect has changed — otherwise the hide→POSCHANGED→SETPOS→tray-visible-again loop produces a wait cursor and dead clicks on the top bar. `WorkAreaChanged` only when placement has actually changed. No `ABM_WINDOWPOSCHANGED` on the approved AppBar rect. The dock clamp uses a cached Y (no `Measure`). `ReapplyHide` after the tray icon / idle / `TaskbarCreated`. |
| A second strip stuck on the top bar / the dock jumping up and down | When the hidden taskbar's AppBar narrows the work area, WPF treats the bar as outside `y=0` and pushes it to `y=30`; the old frame stays stuck on the AppBar reservation strip. The dock jumps ~48px on the same push. `WM_WINDOWPOSCHANGING` uses the approved rect / `ClampSlideY` (cached Y; no layout `Measure`); keep-hidden expands the work area with a 1 s backup. On the approved rect, `ABM_WINDOWPOSCHANGED` is skipped. |
| A force kill / closing the console → the taskbar stays hidden | `Stop-Process -Force` skips the restore. **Watchdog (2026-08):** while hiding, the baseline is written to `%LOCALAPPDATA%\WharfBar\taskbar-watchdog.json` and a `WharfBar.exe --taskbar-watchdog` child process watches the PID; if the process dies without a restore, the watchdog shows the tray, applies the state+work-area baseline, and deletes the file (verified: force-kill → the taskbar comes back in ~0.5 s). There is a start-time check against PID reuse; if a new instance rewrites the file, the old watchdog exits without restoring. If a stale file exists at startup, the tray is shown first (self-heal). Closing the `dotnet run` console can also skip WPF `OnExit` — `SetConsoleCtrlHandler` + `run.bat` starts the EXE **detached**. **What the watchdog does not cover:** the AppBar reservation (`ABM_REMOVE` cannot be done with a dead hwnd) — if a ghost strip remains on the top edge, an `explorer.exe` restart is required. Use a normal Quit |
| Force-killing WharfBar to install, upgrade or uninstall it | A hard kill skips `ABM_REMOVE`, so the reserved top strip stays until Explorer restarts (row above). `installer/WharfBar.iss` therefore never force-closes the app: Setup and uninstall run `WharfBar.exe --quit`, and `QuitChannel` asks the running instance to shut down through its normal exit path (taskbar restore + AppBar removal) and waits on the single-instance mutex — released last in `App.OnExit` — so exit code `0` means the shell is already restored (10 s timeout; `1` = still running / cannot be asked, `2` = unexpected error). Setup aborts instead of replacing files under a live instance; a build older than `--quit` must be quit from the tray. Detail: [`07-packaging-and-releases.md`](07-packaging-and-releases.md) |

| A UI action crashes the app in a restricted launch (APPCRASH `0xe0434352`) | `ConfigService.Save` threw `UnauthorizedAccessException` on the `%AppData%\WharfBar\config.json` write — the low-integrity token of a restricted launch cannot write medium-integrity profile data — and the tab-change event handler had no catch, so the WPF dispatcher unwound into an unhandled exception (event log: Application Error 1000, `KERNELBASE.dll`; WER dump in `%LOCALAPPDATA%\CrashDumps\WharfBar.exe.<pid>.dmp`). Fixed: `ConfigService.Save` catches `IOException`/`UnauthorizedAccessException`/`JsonException`, keeps the in-memory config authoritative (`LastSaveError`) and lets the app run; the Startup-shortcut write is likewise best-effort. `CrashLog.Install()` (first thing in `OnStartup`) writes dispatcher/app-domain/task unhandled exceptions — with the process integrity RID — to `%LOCALAPPDATA%\WharfBar\logs\`, falling back to `%TEMP%` and the app folder. To diagnose an APPCRASH that predates the log: `dotnet-dump analyze %LOCALAPPDATA%\CrashDumps\WharfBar.exe.<pid>.dmp -c "clrstack -all" -c "exit"` — the managed stack names the throwing handler. |
| WharfBar opens, but the Windows taskbar stays visible and the top bar overlaps the desktop / maximized windows instead of reserving the strip | The process token is **below medium integrity** (a sandboxed terminal or low-integrity parent launched it). UIPI silently drops the shell calls — `ShowWindow(Shell_TrayWnd, SW_HIDE)`, `SHAppBarMessage(ABM_NEW/SETPOS)`, `SetWindowLong` — so the taskbar cannot be hidden and the AppBar cannot reserve the top edge; the bar then just floats over the desktop. Startup checks `ProcessIntegrity` and warns (Continue/Quit) instead of running a mismatched desktop. To diagnose a launch, check the process integrity label (`ProcessIntegrity.TryGetCurrentRid` or Process Explorer); start WharfBar normally (Explorer, `run.bat` from a normal terminal) or copy the build out of the sandboxed folder. **Measured (2026-11-08):** an executable under the repository folder gets RID `0x1000` (low) however it is started — agent/sandboxed terminal, `dotnet run`, or even an Explorer double-click — while the same binary copied to `%TEMP%` or `%LOCALAPPDATA%` starts at `0x2000` (medium); `whoami`, `cmd` and `dotnet exec` stay medium in the same shell. So the *workspace path itself* is sandboxed: a run started in place always trips the guard and cannot save settings. Use `run.bat` (it builds, copies the output to `%LOCALAPPDATA%\WharfBar\run` and starts that copy) or copy the build out of the workspace by hand and start it there; a bare `dotnet run`, `bin\Debug\WharfBar.exe`, or an Explorer double-click inside the repo still starts the sandboxed exe. The app cannot fix this itself: Windows blocks a restricted token by design |

## Development tip

If you crash often while working with an AppBar, a stuck area is normal. Restarting Windows Explorer from Task Manager usually fixes it. The lasting fix is still a correct `ABM_REMOVE` and re-registration path.
